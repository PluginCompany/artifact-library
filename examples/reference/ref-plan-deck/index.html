Context · v0.4.0

The library works well for ten artifacts. Not for a hundred.

Works today
  • Stable links and immutable version snapshots
  • Grid & list homepage with search, sort and time filter
  • Server-made previews from one background Chromium worker
  • Agent-friendly CLI: every command speaks --json
Breaks as it grows
  • No grouping. A guide, a tour and a report about one department are three unrelated cards.
  • Metadata-only search. Content inside pages can't be found.
  • No tags. The only filter is “updated since”.
  • 24 cards per page. Past one page, browsing turns into scrolling.

Everything on the left is shipped and stays. The right column is what this plan addresses.

  • 24 cards per page: src/library.ts requests limit=24.
  • One preview worker: src/previews.ts.
Scope

Three goals. Four things we deliberately won't do.

01

Group

Named, ordered collections. An artifact can live in several.

02

Label

Free-form, normalised tags, set at publish time or later.

03

Find

Full-text search over page content, ranked, with snippets.

Non-goals for v0.5
  • Accounts, permissions, private collections
  • Semantic / vector search
  • Searching historical versions
  • Indexing PDFs and other binaries

Non-goals keep the trusted-network, no-database design intact. Each could be a later release.

User stories

Four people, four moments that are slow today.

Agent

Publishes into the right place

“I publish a report with --tag report --collection workshop so people find it next to its siblings.”

Team lead

Opens one link for a topic

“I share the Workshop collection and everyone sees the handbook, tour and reports in order.”

Anyone

Finds a phrase, not a title

“I search torque settings and land on the right page of the handbook, with a snippet.”

CLI user

Scripts against search

“artifact search rework --tag report --json returns ranked hits with page paths.”

Each story maps to one phase: agent + team lead → tags and collections, anyone + CLI user → full-text search.

Approach

Additive changes on the architecture we already have.

Exists in v0.4New in v0.5
1

Tags ride on the catalog. One new field in artifact.json; edits bump the revision like any metadata change.

2

Collections are small JSON files next to the catalog, with their own revision for safe concurrent edits.

3

The preview worker learns a second job. It already renders each snapshot; now it also extracts the visible text.

4

The index is a cache. Delete it and it rebuilds from snapshots. No new source of truth.

Key design choice: reuse the rendered DOM from the preview browser instead of parsing HTML. Many of the best artifacts build their content in JavaScript; most of the reference collection does.

No database is introduced as a source of truth. The index is derived data.

Appendix A

API & CLI sketch

# tag and file at publish time
artifact publish ./report --slug q3-ops \
  --tag report --tag workshop \
  --collection workshop
artifact metadata set q3-ops \
  --add-tag q3 --expected-revision 4

# collections
artifact collection create workshop \
  --title "Workshop"
artifact collection add workshop \
  e-bike-tour --after workshop-handbook

# search page content
artifact search "torque settings" --tag guide --json
GET  /api/v1/artifacts?tag=report&collection=workshop
GET  /api/v1/search?q=torque+settings&limit=20
     → { hits: [{ slug, version, path,
                  title, snippet, score }] }
GET  /api/v1/collections
PUT  /api/v1/collections/:slug
     { title, items: [slug…], expectedRevision }
GET  /api/v1/server
     → capabilities += tags, collections, search

# unchanged: apiVersion 1, cursors, sorts,
# updatedSince, limit 1–100
