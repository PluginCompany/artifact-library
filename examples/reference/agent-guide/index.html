Make artifacts people actually read

An artifact is a web page you publish so a person can read, review or answer your work later — at a stable link, with every version kept. This guide is how to make one that is worth opening: when to make it, which reference to copy, how to write it for the person who reads it, how to show instead of describe, how readers answer you on the page, and how to review it before you share it.

Server
Static HTML, CSS, JS and assets per artifact; immutable versions; a toolbar is injected for version switching.
Saving
Pages save comments, answers and verdicts beside the artifact; you read them with artifact feedback.
Look
One shared kit for every page: tokens, components, charts, self-hosted fonts.
Access
Anyone who can reach the server can read every artifact and save answers and comments on it. If the server sets ARTIFACT_TOKEN, publishing, updating, archiving and purging need that token. No accounts.

The 60-second version

  1. Search first. Something may already exist: artifact search "<topic>" --json. Update it instead of starting over.
  2. Name the reader and the job. Who opens the link, and what must they do with it: approve, choose, verify, follow along?
  3. Pick a reference by job from section 04 and download it: artifact download <ref-slug> --out ./my-artifact. Change the content, not the plumbing.
  4. Write for that reader. Conclusion and request on the first screen, a chapter menu, short plain paragraphs, and a table, diagram or chart wherever something is compared, flows or is counted (05, 06).
  5. Publish, then review it. artifact lint <slug> --screenshots ./shots; fix every error, look at the images, artifact update.
  6. Share the link with two lines: what it is and what you need. Then read what they saved with artifact feedback <slug>, reply in the threads and update at the same link.
artifact search "release plan" --json
artifact download ref-plan-deck --out ./release-plan
# edit ./release-plan/index.html and data.js, then:
artifact publish ./release-plan --slug release-plan-0-4 \
  --title "Release plan 0.4" \
  --description "Scope, milestones and risks for the 0.4 release of the artifact service." --json
artifact lint release-plan-0-4 --screenshots ./shots     # fix, then artifact update
artifact feedback release-plan-0-4

When to make an artifact — and when not

Make one when
  • The user will read it more than once, or show it to someone else.
  • Your work needs evidence to be trusted: screenshots, test output, a diff walked through.
  • There are numbers that deserve a chart and a table.
  • You need answers to several decisions — ask on a page instead of in a wall of chat.
  • A task runs long and someone wants to follow it without asking “how far are you?”.
  • The explanation needs layout: a diagram, a timeline, side-by-side options.
Don't make one when
  • The answer fits in a few lines of chat.
  • It belongs in the repository (a README, an ADR the team keeps in git) — put it there and link it.
  • It contains secrets, credentials, customer or personal data.
  • You won't take the time to verify it — an unchecked page costs the reader more than no page.
  • An artifact on the topic already exists — update that one.

The workflow

Nine steps. Skipping 1, 5 or 8 is how artifacts go wrong.

  1. Search for existing work

    Every word must match the slug, title or description. If you find it, download it and continue at step 4 with an update.

    artifact search "toolbar redesign" --json
artifact recent --limit 10 --json

  2. Pick a reference by the job, not the format

    “Show a reviewer what I built” → implementation review, not “a page with screenshots”. Use the picker.

  3. Download it into a fresh folder

    Downloads contain the original files including kit/ and fonts, so the copy works offline straight away.

    artifact download ref-implementation-review --out ./review-search-feature

  4. Write the content for the reader

    Follow the EDITING GUIDE comment and section 05: the conclusion and your request on the first screen, a chapter menu, plain short paragraphs, and the blocks for anything compared, ordered or counted. Measure what you can; label anything invented as Example content. Never edit files inside kit/; add to the artifact's own style.css or app.js.

  5. Publish with good metadata

    A title is a name (“Search feature review”), the description one sentence of what is inside. Keep the slug: it is the permanent link.

    artifact publish ./review-search-feature --slug review-search-feature \
  --title "Search feature review" \
  --description "Acceptance criteria, annotated screenshots and findings for full-text search." --json

  6. Review it — really

    artifact lint renders the published page in the server's browser at 1440 and 390 px and lists what is wrong. Fix every error, look at the screenshots in light and dark, run the checklist, then artifact update.

    artifact lint review-search-feature --screenshots ./shots

  7. Share the link with a short summary

    Send url (always the latest) — not versionUrl — plus two lines: what it is and what you need from the reader. If it collects answers, say: “Answer on the page, then tell me to check the artifact.”

  8. Read what they saved

    When the user says “check the artifact”, read everything — don't guess from the chat.

    artifact feedback review-search-feature
artifact feedback review-search-feature --since 2h --json

  9. Answer and update at the same link

    Reply in the threads they used, resolve what you fixed, then publish a new version. The page shows readers a calm “new version available” notice.

    artifact data append review-search-feature comments.finding-F2 \
  --item '{"text":"Fixed in v3: the dock collapses below 600 px."}' --author "Claude Code"
artifact update review-search-feature ./review-search-feature --message "Fixed F2 and F3" --json

Write for the reader

Styling comes from the kit. Whether anyone acts on the page depends on the content: who it is for, what it concludes, and how quickly a reader finds what they need.

Name the reader and the job

Before writing, decide who opens the link and what they must do with it: approve a plan, pick an option, verify finished work, follow progress. Every chapter serves that job; the rest goes to an appendix or nowhere.

Conclusion first

The first screen says what the page is, the conclusion or proposal in one or two sentences, what you need from the reader and where, and the status. Reasons come after, not before.

A chapter menu

Every chapter is a <section id> with an <h2>. With three or more, add <nav class="topnav" data-toc> to the top bar (or a side nav for long pages); the kit links every chapter and highlights the current one.

Plain and short

Full sentences, one idea per paragraph, at most about four lines. Use the words the reader uses; define a term once or drop it. Numbers beat adjectives: “about four working days”, not “moderate effort”.

Measure, cite, label

If you can count it, time it or run it, do, and say how. Point to files and lines (src/catalog.ts:42). Mark estimates as estimates and invented content as Example content.

Decisions on the page

Turn open questions into options with trade-offs and a recommended default, plus a verdict when you need approval (ref-decision-questionnaire). Say that answers are saved and reach you.

Shorthand

Reacquire the artifact lock and check existence, latestVersion, digest and revision before writing. Never mix old/new versions. Discard stale jobs and requeue.

For the reader

Before the index is updated, the job checks that the artifact still exists and that nobody published a newer version in the meantime. If someone did, it throws its work away and starts again for the new version, so the index never mixes text from two versions.

Shorthand

Static pass + optional rendered pass; dedupe; bounded budgets.

For the reader

Text is read straight from the HTML files, and also from the page as the browser shows it when the server has a browser. The two are merged without duplicates, and each page contributes at most 256 KB, so one huge page cannot slow search down.

What changes, what staysReaders worry most about what breaks. Next to every proposal, say what changes for them and what stays exactly as it is.

Show, don't describe

When a chapter explains something with a shape, draw the shape. A chapter of more than about 300 words with no table, diagram, chart or figure needs one. The style guide shows these blocks live.

Rules that keep pages consistent

  • Colours only from tokens: --ink, --muted, --accent, --thread, --good/--warn/--bad, series --s1…--s5. Dark mode then works for free.
  • Bricolage Grotesque for headings, Noto Sans for text, JetBrains Mono for labels — all bundled in kit/fonts.
  • Signature details: mono uppercase eyebrows, dashed “stitch” lead-ins on section headings, cards that lift on hover. In page CSS, use the theme tokens for them (var(--label), var(--rule), var(--w-heavy)) so a theme can restyle the page too.
  • Changeable content in data.js; an EDITING GUIDE comment at the top of index.html.
  • Page-specific CSS in the artifact's style.css. Never edit the copy of kit/.

Charts

  • Kit.chart.line | column | bar | donut | spark — SVG, hover tooltips, theme-aware.
  • Wrap each in .chart-card with a title, a one-line takeaway and button.as-table for the table view.
  • Series colours follow fixed slots; pin one with { slot: 2 } so filtering never repaints the others.
  • A legend for two or more series. One y-axis — two measures means two charts.
  • Text in ink colours, never in the series colour. Status colours only for status, always with a word.

Bold or Clean

Every kit page comes in two styles. Bold is the default look above. Clean (kit/themes/clean/) is a calm, professional documentation look: flat white page, hairline borders, small radii, semibold Inter headings, one blue accent. Readers can switch with the Bold / Clean button the kit adds next to the light/dark toggle; you only pick the default. Make Clean the default for plans, specs, reviews and reports that should read like product documentation by linking it after every other stylesheet:

<link rel="stylesheet" href="kit/kit.css">
<link rel="stylesheet" href="style.css">
<link rel="stylesheet" href="kit/themes/clean/clean.css">

Saving & feedback

Readers answer on the page; you read and reply from the CLI. No copying back and forth.

1You publish a page that asks something
2The reader answers, comments or approves on the page
3They tell you “check the artifact”
4artifact feedback <slug>
5You reply in the thread and update the page

How it works

  • Data is a set of small JSON documents stored beside the artifact, not inside a version — it survives every update and is never part of a download.
  • Each document has a key, a value, a revision, timestamps, an author and a role (human from pages, agent from the CLI).
  • Opened from disk or another host, pages fall back to browser storage and say “Saved in this browser only”. Only the server copy reaches you.
  • Limits: keys of 1–128 letters, digits, . _ -; 256 KiB per document; 500 documents per artifact; 1,000 items per thread. Uploads: 500 MB and 10,000 files per publish by default (server settings MAX_UPLOAD_BYTES, MAX_FILES).

Key conventions

KeyValue
comments.<anchor>{ items: [{ id, author, role, createdAt, text, resolved? }] }
answer.<question>{ choice, note } — one document per question
review.<item>{ verdict: "approved" | "changes" | "question", note }
state.<name>Anything live: a run's progress, a runbook's ticks, a chosen scope

Each reference lists its exact keys in its EDITING GUIDE comment.

On the page

// A comment thread under a finding
Kit.comments(document.querySelector("#thread-F2"), { key: "finding-F2", title: "Discussion" });

// Save an answer, show who saved it
await Kit.data.set("answer.q1", { choice: "b", note: "Prefer the pill" });

// Re-render when anyone (or the agent) changes something
Kit.data.watch("state.", (docs) => render(docs), { interval: 5000 });

Add <span data-save-status></span> to the top bar so readers see that their answer reached the server.

From the CLI

# read everything, or only recent changes
artifact feedback my-review
artifact feedback my-review --since 2h --json

# reply as yourself, then resolve
artifact data append my-review comments.finding-F2 \
  --item '{"text":"Fixed in v4","replyTo":"c1eac54f3bc8"}' --author "Claude Code"
artifact data update-item my-review comments.finding-F2 c1eac54f3bc8 \
  --changes '{"resolved":true}' --author "Claude Code"

# publish live state for a run log (the page polls it)
artifact data set my-run state.run --file run.json --author "Claude Code"
ConcurrencyThread replies use append, which never loses a concurrent comment. For whole documents, pass --expected-revision <n> (0 = must not exist yet); a DATA_CONFLICT (exit 2) means someone saved in between — read it again and merge.
PrivacyEveryone who can reach the server can read every artifact and save data on it, even when a write token protects publishing. Archiving hides an artifact, and only artifact purge removes it for good. Never publish or ask for secrets, credentials or personal data.

Review before sharing

Publish, run artifact lint, fix, update, then read the page as the reader would. Tick the checklist as you go; ticks are remembered in this browser only.

    Lint the published page

    The server opens the page in its browser at 1440 and 390 px and reports console errors, horizontal scroll, a missing chapter menu, walls of text, missing title or description, and broken links and images. A non-zero exit code means errors. Then look at the screenshots: a page without lint errors is not yet a page that reads well.

    artifact lint my-review
artifact lint my-review --screenshots ./shots --json
    No lint on this server? Screenshot it yourself

    Older servers and the slim image (no browser) cannot lint. Playwright does the same job locally.

    python3 - <<'EOF'
import asyncio
from playwright.async_api import async_playwright
URL = "https://artifacts.example.ts.net/artifacts/my-review/"
async def main():
    async with async_playwright() as p:
        b = await p.chromium.launch()
        for w, h, scheme in [(1440, 900, "light"), (1440, 900, "dark"), (390, 844, "light")]:
            page = await b.new_page(viewport={"width": w, "height": h}, color_scheme=scheme)
            errors = []
            page.on("pageerror", lambda e: errors.append(str(e)))
            await page.goto(URL); await page.wait_for_timeout(1200)
            wide = await page.evaluate("document.documentElement.scrollWidth")
            await page.screenshot(path=f"shot-{w}-{scheme}.png", full_page=True)
            print(w, scheme, "scrollWidth", wide, "errors", errors)
        await b.close()
asyncio.run(main())
EOF

    Publish & update

    Titles, descriptions, slugs

    WeakStrong
    TitleReport v2 FINALQ3 operations report
    DescriptionHere is the report you asked for.Repairs, comebacks and staffing for the workshop, July–September 2026.
    Slugreport2ops-report-2026-q3
    • Slugs are 1–100 lowercase letters, digits and single hyphens, and permanent.
    • One slug per living document. Recurring things (weekly digests, per-task reviews) get a slug each.
    • Titles and descriptions can also come from <title> and <meta name="description">; explicit flags win.

    Versions, revisions, conflicts

    • version numbers content snapshots; revision is a concurrency token that also changes on metadata edits. Don't assume they are equal.
    • Each update is a complete snapshot: files you leave out disappear from latest but stay in history. Identical content creates no version.
    • Tracked folders (published or downloaded by the CLI) remember their revision. From an untracked folder, read the revision with artifact info and pass --expected-revision.
    • On REVISION_CONFLICT someone published in between: artifact diff <slug> --local ./dir or download the newer version, merge, and update with its revision. Never bump the number blindly.
    • A lost response? The CLI saved the upload: artifact retry <operation-key> from the error message — don't publish again.
